GitHub Copilot Proxy 캡처 PoC

사내 CA 기반 TLS 인터셉트 프록시(mitmproxy)로 GitHub Copilot 트래픽의 요청/응답을 캡처하고, 메타데이터(개발자·시간·모델·토큰)·민감정보 마스킹·보존정책·조회 CLI·실시간 대시보드· 호출 프로세스/프로젝트 귀속까지 제공하는 동작하는 구현체입니다.

프록시 127.0.0.1:10801 대시보드 127.0.0.1:10802 mitmproxy 12.2.3 Python 3.13 저장소 SQLite 테스트 32 cases

개요

GitHub Copilot Proxy 캡처 PoC는 GitHub Copilot 관련 네트워크 트래픽을 로컬 TLS 인터셉트 프록시로 통과시키고, allowlist에 해당하는 Copilot 호스트의 요청/응답 payload와 운영 메타데이터를 SQLite에 저장하는 검증용 구현체입니다. 프로젝트 루트의 032-github-copilot-proxy-architecture-2026-06-02.html에서 정리한 “사내 CA 기반 TLS 인터셉트 Proxy로 Copilot 프롬프트와 응답을 수집·관제할 수 있는가”라는 아키텍처 가설을 실제 코드로 확인하는 것이 목적입니다.

서비스는 개발자 PC 또는 현재 셸의 Copilot 호출을 http://127.0.0.1:10801 프록시로 라우팅하고, mitmproxy가 사내 CA 역할의 인증서로 TLS를 복호화한 뒤 addons/capture.py 애드온의 response 훅에서 캡처 여부를 결정합니다. 캡처 대상은 config.yaml의 allowlist_hosts로 제한되며, 기본값은 api.githubcopilot.com, copilot-proxy.githubusercontent.com, .githubcopilot.com, proxy.enterprise.githubcopilot.com입니다. 특히 .로 시작하는 항목은 해당 도메인 자체와 하위 도메인을 포함하는 suffix 매칭으로 처리됩니다.

저장 레코드는 단순 payload 덤프가 아니라 개발자 식별자, 클라이언트 IP, 호출 호스트·메서드·경로, HTTP 상태, 요청 모델, 토큰 수, 토큰 산정 출처, 마스킹 여부와 마스킹 히트 수, 호출 프로세스 PID·프로세스명·프로젝트 디렉터리, mitmproxy flow ID를 함께 포함합니다. 기본 저장소는 프로젝트 루트 기준 data/captures.db이며, SQLite 스키마와 조회·집계·보존정리는 ghcp_proxy/storage.py가 담당합니다.

이 PoC는 저장 전 민감정보 마스킹, 토큰 산정, 보존정책, 조회 CLI, 실시간 대시보드, 호출 프로세스·프로젝트 귀속까지 한 번에 검증합니다. 마스킹은 정규식 기반 best-effort 방식이고, 토큰 산정은 tiktoken이 설치되어 있으면 cl100k_base 인코딩을 사용하며, 없으면 평균 4 chars/token 휴리스틱으로 추정합니다. 응답 payload에 OpenAI 호환 usage가 포함되어 있으면 그 값을 우선 사용합니다.

PoC 성격: 이 프로젝트는 사내 보안·프라이버시·법무 검토를 대체하는 운영 제품이 아니라, Copilot 트래픽을 TLS 인터셉트 프록시로 관측하고 필요한 메타데이터를 생성할 수 있음을 검증하는 로컬 기준 참조 구현입니다. 실제 전사 적용 시 인증서 배포, 접근통제, 저장 암호화, DLP 연계, 감사 정책, 보존·파기 정책을 별도로 설계해야 합니다.

요구사항

요구사항은 프로젝트 루트의 근거 문서 032-github-copilot-proxy-architecture-2026-06-02.html와 현재 구현체의 README·설정·코드를 기준으로 정리했습니다. 핵심 결론은 “GitHub Copilot도 사내 CA 기반 TLS 인터셉트 Proxy를 사용하면 요청/응답 payload를 캡처할 수 있지만, custom certificate 없이 단순 프록시만 경유하면 payload 내용 검사는 불가능하다”입니다.

비기능 요구사항과 제약

구분 요구/제약 설명
보안 사내 CA 기반 TLS 인터셉트는 강한 통제 전사 PC가 사내 CA를 신뢰하게 되면 해당 CA 발급자가 TLS 트래픽을 복호화할 수 있습니다. 운영 전 인증서 배포·보관·폐기·감사 정책이 필요합니다.
프라이버시 프롬프트 원문에는 개인·업무 민감정보가 포함될 수 있음 개발자 질문, 코드 조각, 파일 경로, 이메일, 토큰 등이 포함될 수 있으므로 최소수집, 목적 제한, 접근권한 분리, 열람 로그가 필요합니다.
법무/컴플라이언스 원문 저장·분석 전 내부 정책 검토 필요 근거 문서와 README 모두 실제 적용 전 보안·프라이버시·법무 검토를 명시합니다. PoC 결과를 운영 근거로 사용하려면 조직 정책 승인이 선행되어야 합니다.
데이터 보호 마스킹은 best-effort 현재 정규식 룰은 대표 패턴을 줄이는 용도입니다. 운영 수준에서는 DLP 엔진, 사내 비밀 패턴, 암호화 저장, 권한 기반 조회가 추가로 필요합니다.
정확성 토큰과 프로젝트 귀속은 상황에 따라 추정 응답 usage가 없으면 토큰은 추정치입니다. IDE는 공유 소켓을 사용할 수 있어 워크스페이스 귀속이 best-effort일 수 있습니다. 터미널/CLI 호출은 cwd 기반으로 더 정확합니다.
네트워크 호환성 Proxy URL은 http:// 전제 근거 문서의 공식 조건은 Copilot 프록시 URL을 http://로 제공하는 것입니다. 인증은 Basic 또는 Kerberos를 전제로 설명됩니다.
캡처 범위 제한 allowlist 기반 최소 캡처 macOS 시스템 전체 프록시를 설정하더라도 저장은 Copilot allowlist 호스트로 제한합니다. 이는 불필요한 일반 웹 트래픽 저장 위험을 낮추기 위한 설계입니다.
중요: GitHub Copilot Metrics API 같은 native usage metrics는 조직 단위 집계 지표 확인에는 유용하지만, 프롬프트 원문을 제공하지 않는다는 점을 근거 문서가 명시합니다. 따라서 “원문 payload 저장” 요구는 native 기능이 아니라 TLS 인터셉트 프록시 경로로 분리해 설계해야 합니다.

주요 경계와 책임

영역 책임 포트/데이터
클라이언트 프록시 설정 VS Code, 터미널, CLI가 Copilot 요청을 로컬 mitmproxy로 보내도록 구성합니다. HTTP_PROXY, HTTPS_PROXY, macOS web/secure web proxy
mitmproxy TLS를 복호화하여 요청과 응답 본문을 애드온에서 읽을 수 있게 합니다. 캡처 실패가 통신 자체를 막지 않도록 예외를 로깅하고 반환합니다. 기본 listen port 10801
allowlist 필터 Copilot 관련 호스트만 저장 대상으로 제한합니다. 일치하지 않으면 캡처하지 않고 흐름을 통과시킵니다. allowlist_hosts, suffix 매칭
캡처 파이프라인 모델 추출, 프로세스/프로젝트 귀속, 토큰 산정, 마스킹, 본문 크기 제한, 레코드 생성을 수행합니다. max_body_bytes 기본 1048576
SQLite 저장소 payload와 메타데이터를 저장하고 recent/get/token_summary/project_summary/purge API를 제공합니다. 기본 data/captures.db
조회 CLI 저장된 데이터를 운영자나 분석 스크립트가 조회할 수 있게 합니다. python -m ghcp_proxy.cli ..., --json
실시간 대시보드 캡처 발생 시 SSE로 행을 추가하고 집계를 갱신합니다. 실시간 이벤트에서는 원문 request/response body를 제거합니다. 기본 127.0.0.1:10802, /events, /api/recent, /api/tokens, /api/projects

설정 예시

allowlist_hosts:
  - api.githubcopilot.com
  - copilot-proxy.githubusercontent.com
  - .githubcopilot.com
  - proxy.enterprise.githubcopilot.com

storage:
  db_path: data/captures.db
  retention_days: 30

masking:
  enabled: true

capture:
  store_response: true
  max_body_bytes: 1048576

dashboard:
  enabled: true
  host: 127.0.0.1
  port: 10802
대시보드 노출 최소화: addons/capture.py는 SQLite에는 마스킹·절단된 payload를 저장하지만, SSE로 push하는 이벤트에서는 request_body와 response_body를 제거합니다. 따라서 실시간 대시보드는 운영 메타데이터와 집계 확인용이며 원문 열람 UI가 아닙니다.

구성요소 맵

파일 구성은 mitmproxy 애드온, 공통 패키지, 설정, 실행·설정 스크립트, 라이브 검증 스크립트로 나뉩니다. 아래 표는 현재 코드 기준 역할입니다.

파일 역할 설계상 중요 포인트
addons/capture.py mitmproxy 애드온의 핵심 캡처 로직입니다. response 훅에서 host allowlist를 확인하고, 요청/응답 본문을 디코딩해 레코드를 생성합니다. 개발자 식별 우선순위는 X-Copilot-User → Proxy-Authorization Basic 사용자명 → client IP입니다. 캡처 실패가 프록시 통신을 막지 않도록 예외를 로깅합니다.
ghcp_proxy/config.py config.yaml과 환경변수를 로드해 dataclass 설정 객체로 제공합니다. GHCP_CONFIG로 설정 파일 경로를 바꿀 수 있고, GHCP_DASHBOARD, GHCP_DASHBOARD_PORT로 대시보드 일부 설정을 재정의합니다. allowlist suffix 매칭을 구현합니다.
ghcp_proxy/masking.py 저장 전 payload에 포함될 수 있는 대표 민감정보를 정규식으로 마스킹합니다. private key, AWS key, GitHub token, OpenAI key, Slack token, bearer/auth, JWT, 이메일을 대상으로 하며, 운영 DLP를 대체하지 않는 PoC 수준 best-effort입니다.
ghcp_proxy/tokens.py 모델 필드 추출, 토큰 추정, 응답 usage 파싱을 담당합니다. tiktoken이 있으면 cl100k_base, 없으면 len(text)/4 휴리스틱을 사용합니다. SSE의 data: {...} 라인도 JSON 후보로 스캔합니다.

엔드투엔드 데이터 흐름

실제 캡처는 mitmproxy의 response 시점에 발생합니다. 요청 본문은 response 훅에서도 접근 가능하므로, 응답이 도착한 뒤 요청·응답 payload와 상태 코드, 모델, usage 정보를 함께 하나의 레코드로 구성합니다. allowlist에 맞지 않는 호스트는 저장하지 않으며, 저장 전 토큰 산정은 마스킹 전 원문 기준으로 수행됩니다.

단계별 상세

  1. 클라이언트 라우팅: VS Code/터미널/CLI는 시스템 프록시나 HTTP_PROXY, HTTPS_PROXY 환경변수를 통해 127.0.0.1:10801로 요청을 보냅니다. Node 기반 도구의 CA 신뢰 보조 경로로 NODE_EXTRA_CA_CERTS를 사용할 수 있습니다.
  2. TLS 인터셉트: mitmproxy가 클라이언트와 업스트림 사이에서 TLS를 복호화·재암호화합니다. 이 단계가 있어야 payload를 읽을 수 있으며, custom certificate 없이 단순 라우팅만 하는 경우 내용 검사는 불가능합니다.
  3. response 훅 진입: addons/capture.py의 response(flow)가 호출되고, flow.request.pretty_host가 설정의 allowlist와 일치하는지 검사합니다.
  4. payload 추출: 허용된 호스트이면 요청 원문을 UTF-8 replacement 방식으로 디코딩합니다. capture.store_response가 true이고 응답이 있으면 응답 본문도 디코딩합니다.
  5. 모델 추출: 요청 JSON 또는 SSE 유사 본문에서 model 필드를 best-effort로 찾고, 없으면 unknown으로 기록합니다.
  6. 프로세스·프로젝트 귀속: flow의 client peername에서 소스 포트를 얻고, lsof 기반 스냅샷/조회로 PID와 프로세스명을 찾습니다. cwd가 프로젝트로 보이면 그대로 사용하고, VS Code류 공유 프로세스는 열려 있는 워크스페이스와 요청 본문 경로로 보정합니다.
  7. 토큰 산정: 요청 토큰은 마스킹 전 원문으로 먼저 산정합니다. 응답에 usage.total_tokens가 있으면 api_usage로 기록하고 prompt/completion/total 값을 우선합니다. 없으면 응답 본문도 추정해 합산합니다.
  8. 마스킹: 설정상 masking.enabled가 true이면 요청·응답 본문에 마스킹 룰을 적용하고, 총 치환 횟수를 mask_hits에 기록합니다.
  9. 본문 크기 제한: capture.max_body_bytes를 초과하는 요청·응답 본문은 UTF-8 바이트 기준으로 절단하고 …[truncated] 접미사를 붙입니다.
  10. SQLite 저장: CaptureRecord를 생성해 captures 테이블에 삽입합니다. 저장 성공 후 생성된 row id가 캡처 ID가 됩니다.
  11. 실시간 push: 대시보드가 활성화되어 있으면 레코드를 dict로 바꾼 뒤 request_body와 response_body를 제거하고 SSE 클라이언트에 broadcast합니다.
  12. 조회와 보존: 운영자는 CLI 또는 대시보드 API로 최근 목록·토큰 집계·프로젝트 집계를 조회하고, purge 명령으로 보존기간을 지난 데이터를 삭제할 수 있습니다.

내부 동작: mitmproxy 캡처 애드온

addons/capture.py는 mitmproxy의 애드온 인스턴스(addons = [CopilotCapture()])로 로드되어 Copilot 관련 응답을 가로채고, 요청/응답 본문·토큰·귀속 정보를 SQLite와 실시간 대시보드로 전달한다. 캡처 실패가 프록시 통신을 막지 않도록 response() 훅 전체를 try/except로 감싼다.

애드온 초기화와 생명주기

  • load_config()로 allowlist, 저장소, 마스킹, 대시보드 설정을 읽는다.
  • Storage는 설정된 DB 경로를 열고 스키마/마이그레이션을 적용한다.
  • Attributor는 생성 시 백그라운드 소켓 스냅샷 폴러를 시작한다.
  • 대시보드가 활성화되어 있으면 DashboardServer.start()로 HTTP/SSE 서버를 데몬 스레드에서 시작한다.
  • done()은 attributor 중지, dashboard 종료, storage close를 각각 best-effort로 수행한다.

response 훅과 allowlist 필터

def response(self, flow) -> None:
    try:
        host = flow.request.pretty_host
        if not self.cfg.host_allowed(host):
            return
        self._capture(flow)
    except Exception:
        logger.exception("capture 처리 중 오류")

필터는 설정의 host_allowed()에 위임된다. 기본값은 api.githubcopilot.com, copilot-proxy.githubusercontent.com, .githubcopilot.com이며, allowlist에 맞지 않는 호스트는 즉시 반환한다.

  1. 요청 본문은 항상 decode하고, 응답 본문은 capture.store_response가 참이고 flow.response가 있을 때만 decode한다.

  7. CaptureRecord에 메타데이터, 귀속 컬럼, payload, flow id를 담아 저장한다.
  8. SSE 이벤트에는 request_body, response_body를 제거한 레코드만 전송한다.

ghcp_proxy/attribution.py는 모든 트래픽이 로컬 프록시(127.0.0.1)를 거친다는 전제에서 클라이언트 소스 포트를 PID로 역추적한다. 핵심 경로는 소스 포트 → PID/프로세스명 → cwd → 프로젝트 디렉터리이며, VS Code 공유 헬퍼와 요청 본문 경로를 보조 신호로 사용한다.

백그라운드 established 연결 스냅샷

Attributor는 기본적으로 데몬 스레드를 시작하고 1초마다 lsof -nP -iTCP -sTCP:ESTABLISHED를 실행한다. 결과를 파싱해 sport -> (timestamp, pid, process) 스냅샷을 만들고, snap_evict 기본 4초보다 오래된 항목을 제거한다.

def _snapshot_once(self) -> None:
    out = _run(["lsof", "-nP", "-iTCP", "-sTCP:ESTABLISHED"], timeout=3.0)
    now = time.time()
    with self._snap_lock:
        for line in out.splitlines()[1:]:
            parts = line.split()
            if len(parts) < 9:
                continue
            pid = int(parts[1])
            if pid == _SELF_PID:
                continue
            name = next((f for f in parts if "->" in f), "")
            if "->127.0.0.1:" not in name or not name.startswith("127.0.0.1:"):
                continue
            sport = int(name.split("->", 1)[0].split(":")[1])
            self._snap[sport] = (now, pid, os.path.basename(parts[0]))
lsof 파싱 주의점: -sTCP:ESTABLISHED를 쓰면 출력 끝에 (ESTABLISHED) 상태 컬럼이 붙는다. 따라서 NAME이 항상 마지막 필드라고 가정하지 않고, ->를 포함하는 필드를 찾아 로컬 127.0.0.1:sport->127.0.0.1:port 형태인지 확인한다.

프로젝트 디렉터리 판정

is_project_dir()는 홈 디렉터리 아래 경로만 인정하고, /Library/, /Application Support/, /.Trash, /System/, /usr/, /private/, /Applications/가 포함된 경로를 제외한다. 또한 홈 바로 아래 1단계 경로는 프로젝트 루트로 보지 않고, 홈 기준 깊이 2 이상(rel.count("/") >= 1)을 요구한다.

def mask_text(text: str) -> tuple[str, int]:
    if not text:
        return text, 0
    total = 0
    for _name, pattern, repl in _RULES:
        text, n = pattern.subn(repl, text)
        total += n
    return text, total

def estimate_tokens(text: str) -> int:
    if not text:
        return 0
    if _ENC is not None:
        try:
            return len(_ENC.encode(text))
        except Exception:
            pass
    return max(1, round(len(text) / 4))

요청 모델과 응답 usage 추출

  • model_from_request(body)는 본문에서 JSON 객체 후보를 순회하며 최상위 model 문자열을 반환한다.
  • model_from_response(body)는 동일 방식으로 응답 JSON/SSE에서 model을 찾는다. 요청에 모델이 없거나 “auto” 라우팅이라 확정 모델을 알 수 없을 때, 실제 응답을 서빙한 모델명을 보조로 확인하는 fallback 경로다.
  • usage_from_response(body)는 OpenAI 호환 usage 딕셔너리에서 prompt_tokens, completion_tokens, total_tokens를 추출한다.
  • SSE 응답을 고려해 전체 JSON 파싱에 실패하면 줄 단위로 보고, data: 접두사를 제거한 뒤 JSON을 파싱한다. [DONE]은 건너뛴다.
  • 여러 JSON 후보에 usage가 있으면 마지막 usage를 사용한다.

capture._capture()에서 usage.total_tokens가 있으면 token_source는 api_usage이고 API 제공 값을 우선한다. usage가 없으면 요청/응답 본문 추정치를 더하고 token_source에는 estimator_name() 결과가 들어간다.

def _migrate(self) -> None:

        row[1] for row in self._conn.execute("PRAGMA table_info(captures)").fetchall()
    }
    for col, decl in _EXTRA_COLUMNS.items():

CREATE TABLE IF NOT EXISTS는 이미 존재하는 구버전 테이블에 새 컬럼을 추가하지 않는다. 그래서 PRAGMA table_info로 귀속 컬럼(client_pid, client_process, project_dir, project_source) 유무를 확인해 ALTER TABLE을 먼저 수행한 뒤 project_dir 인덱스를 만든다. 순서가 바뀌면 구버전 DB에서 “no such column: project_dir” 문제가 날 수 있다.

조회·집계·정리 API

  • insert(record): dataclass를 dict로 바꿔 전체 필드를 insert하고 lastrowid를 반환한다.
  • recent(limit): payload를 제외한 주요 컬럼을 id 역순으로 조회한다. 대시보드/CLI 목록이 사용한다.
  • get(capture_id): SELECT *로 payload 포함 단일 캡처를 반환한다. CLI show가 사용한다.
  • token_summary(inference_only=True): developer, model별 호출 수와 토큰 합계를 total_tokens 내림차순으로 집계한다. 기본값은 model='unknown'인 비추론(보조) 트래픽을 제외하며, inference_only=False로 전체를 포함할 수 있다.
  • project_summary(inference_only=True): COALESCE(project_dir,'(unknown)'), COALESCE(client_process,'?')별 호출 수/토큰 합계를 집계한다. 마찬가지로 기본은 비추론 트래픽 제외다.
  • purge(retention_days): 0 이하이면 아무것도 하지 않고, 양수이면 UTC 현재시각에서 보존일을 뺀 cutoff보다 오래된 ts를 삭제한다.

def _stream(self):
    self.send_response(200)
    self.send_header("Content-Type", "text/event-stream")
    self.send_header("Cache-Control", "no-cache")
    self.send_header("Connection", "keep-alive")
    self.end_headers()
    q: queue.Queue = queue.Queue()
    server._register(q)
    try:
        self.wfile.write(b": connected\n\n")
        self.wfile.flush()
        while True:
            try:
                evt = q.get(timeout=15)
            except queue.Empty:
                self.wfile.write(b": ping\n\n")
                self.wfile.flush()
                continue
            payload = json.dumps(evt, ensure_ascii=False)
            self.wfile.write(f"data: {payload}\n\n".encode("utf-8"))

클라이언트마다 queue.Queue를 만들고 서버의 _clients set에 등록한다. 15초 동안 이벤트가 없으면 SSE 주석 형식의 : ping을 보내 연결을 유지한다. 연결이 끊기면 BrokenPipeError, ConnectionResetError, OSError를 삼키고 finally에서 unregister한다.

broadcast(event)는 lock 아래에서 현재 클라이언트 목록을 복사한 뒤 각 큐에 put_nowait()한다. HTTP 서버는 daemon_threads=True로 설정되며, port=0이면 실제 할당 포트를 server_address[1]로 반영한다.

실시간 이벤트 payload에는 원문 요청/응답 본문이 포함되지 않는다. capture._capture()가 asdict(record) 후 request_body, response_body를 제거하고 브로드캐스트해 전송량과 노출면을 줄인다. 단, /api/recent도 storage의 recent()를 쓰므로 payload를 반환하지 않는다.

def host_allowed(self, host: str) -> bool:
    host = (host or "").lower()
    for entry in self.allowlist_hosts:
        entry = entry.lower()
        if entry.startswith("."):
            if host == entry[1:] or host.endswith(entry):
                return True
        elif host == entry:
            return True
    return False

PC 전체 캡처 설정(macOS)

scripts/setup_mac_capture.sh는 이 Mac의 시스템 웹/보안 프록시를 캡처 프록시로 연결한다. 스크립트는 사용자가 직접 실행해야 하며, System 키체인과 네트워크 설정을 변경하므로 sudo 권한이 필요하다.

cd /Users/hacbook/ms/workspace/ghcp-proxy
./scripts/run_proxy.sh &
./scripts/setup_mac_capture.sh

스크립트가 수행하는 작업

  1. .mitmproxy/mitmproxy-ca-cert.pem 존재 여부를 확인한다. 없으면 먼저 프록시를 한 번 실행해 CA를 생성해야 한다.
  2. route -n get default로 기본 라우트 인터페이스를 찾고, networksetup -listnetworkserviceorder로 해당 장치의 네트워크 서비스 이름을 찾는다. 일반적으로 Wi-Fi가 활성 인터페이스이면 Wi-Fi 서비스가 선택된다.
  3. security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain로 mitmproxy CA를 System 키체인에 신뢰 등록한다. 운영에서는 사내 CA를 같은 신뢰 저장소에 배포하는 방식으로 대체한다.
  4. networksetup -setwebproxy와 -setsecurewebproxy로 시스템 HTTP/HTTPS 프록시를 127.0.0.1:10801에 연결하고 상태를 켠다.
  5. 127.0.0.1, localhost, *.local, 169.254/16은 프록시 우회 목록에 넣어 로컬/대시보드 접근을 우회한다.

시스템 프록시를 무시하는 일부 CLI, Node 기반 도구, git에는 현재 셸에 환경변수를 추가 적용한다.

동작 검증

프록시와 시스템 설정이 적용된 뒤 Copilot allowlist 도메인에 요청해 TLS 검증과 프록시 경유 여부를 확인한다. curl은 macOS System 키체인이 아니라 자체 CA 번들을 사용할 수 있으므로, 테스트에는 --cacert로 mitmproxy CA를 명시하는 것이 안전하다.

curl -v \
  --proxy http://127.0.0.1:10801 \
  --cacert .mitmproxy/mitmproxy-ca-cert.pem \
  https://api.githubcopilot.com/
이 설정은 시스템 전체 TLS 인터셉트다. 인증서 pinning을 사용하는 일부 앱은 실패할 수 있다. 문제가 생기면 즉시 캡처 해제 절차를 실행한다.

캡처 해제

cd /Users/hacbook/ms/workspace/ghcp-proxy

스크립트는 두 단계로 동작한다.

  1. sudo networksetup -setwebproxystate <서비스> off와 -setsecurewebproxystate <서비스> off를 실행한다.

호출 프로젝트 귀속 사용

이 PoC는 로컬 프록시 연결의 클라이언트 소스 포트를 기준으로 소켓 소유 PID를 찾고, PID의 프로세스명과 현재 작업 디렉터리(cwd)를 역추적해 호출 프로젝트를 추정한다. 모든 트래픽이 127.0.0.1에서 들어오기 때문에 IP만으로는 프로젝트를 알 수 없어 lsof 기반 매핑을 사용한다.

귀속 우선순위

  1. 소켓 PID의 cwd가 프로젝트 폴더이면 그대로 사용한다. 터미널/CLI 호출은 일반적으로 정확하며 project_source=cwd로 저장된다.
  2. 프로세스명이 VS Code의 공유 헬퍼(Code Helper 등)이고 cwd가 프로젝트가 아니면 열린 워크스페이스를 추론한다. 단일 워크스페이스는 project_source=vscode-workspace, 복수 후보는 project_source=vscode-workspace?로 저장될 수 있다.
  3. 복수 VS Code 워크스페이스 후보가 있을 때 요청 본문에서 파일 경로를 찾고 특정 워크스페이스 하위 경로와 일치하면 project_source=body-path로 좁힌다.
호출 유형저장 예시해석
터미널/CLIclient_process=python3, project_dir=.../ghcp-proxy, project_source=cwd프로세스 cwd 기반이므로 정확도가 높다.
VS Codeclient_process=Code Helper, project_source=vscode-workspace 또는 vscode-workspace?공유 소켓과 다중 창 특성 때문에 워크스페이스 추론은 best-effort다.

라이브 검증에서는 터미널에서 발생한 python3 호출이 ghcp-proxy 프로젝트로 귀속되고, VS Code 계열 호출은 Code Helper 프로세스와 열린 workspace 후보로 귀속되는 형태를 확인했다.

IDE는 단일 공유 소켓으로 다중 창 요청을 보낼 수 있어 개별 요청과 워크스페이스의 1:1 매칭은 보장되지 않는다. 운영에서 정확한 창·프로젝트 식별이 필요하면 클라이언트 측 워크스페이스 ID 헤더 주입 같은 보완책을 검토해야 한다.

전사 확장 가능성: PoC에서 운영으로

이 구현체는 “개발자 1대 PC + 로컬 프록시”를 전제로 한 PoC입니다. 프록시(127.0.0.1:10801), 대시보드(127.0.0.1:10802), 저장소(단일 SQLite 파일)가 모두 한 머신에 묶여 있고, 호출 프로세스/프로젝트 귀속은 lsof로 localhost 소스 포트→PID를 역추적하는 방식이라 프록시와 클라이언트가 같은 머신에 있을 때만 정확합니다. 따라서 “회사에서 확장해 쓸 수 있는가”라는 질문의 답은 “구조적으로 가능하지만, 그대로 복제하는 방식이 아니라 몇 개 구성요소를 운영용으로 교체·보강하는 방식”입니다.

핵심 동작(사내 CA로 TLS 인터셉트 → allowlist 호스트 선별 → 모델·토큰 산정 → 마스킹 → 메타데이터 저장 → 조회/대시보드)은 규모와 무관하게 그대로 유지됩니다. 전사 확장에서 바뀌는 것은 ① 프록시를 어디에 두는가(토폴로지), ② 데이터를 어디에 모으는가(중앙 수집), ③ 개발자·프로젝트를 어떻게 식별하는가(귀속 방식), ④ 인증서·프록시 설정을 어떻게 배포하는가 (MDM/GPO)의 네 축입니다.

설계 원칙: 애드온은 캡처 파이프라인의 각 단계(귀속·토큰·마스킹·저장·브로드캐스트)를 독립 모듈로 분리해 두었습니다(ghcp_proxy/*.py). 덕분에 전사 확장은 “전면 재작성”이 아니라 저장 sink 교체, 식별 로직 교체, 마스킹 엔진 교체 같은 지점별 치환으로 접근할 수 있습니다.

혼합형이 현실적: 다수 조직은 중앙 집중형으로 캡처·집계하되, 정확한 프로젝트 귀속이 필요한 경우에 한해 클라이언트가 워크스페이스/리포 식별 헤더를 주입하는 혼합 방식을 씁니다. PoC의 헤더 우선 식별 설계(X-Copilot-User → Proxy-Authorization → IP)가 이 확장의 출발점입니다.

코드 확장 포인트

운영 전환 시 손대는 위치는 대부분 정해져 있습니다. 각 모듈의 경계가 명확해 치환 범위가 좁습니다.

확장 축PoC 현재운영 확장 방향손대는 위치

단계별 도입 로드맵

단계범위핵심 작업활용하는 PoC 자산
0. PoC 검증 개발자 1~수명, 로컬 현재 구현체로 캡처·토큰·귀속·마스킹 동작 확인, 보안/법무 사전 검토 착수 전체 그대로
1. 파일럿 1개 팀(~10명) 중앙 수집 sink 1종(HTTP/SIEM) 추가, 헤더 기반 개발자 식별 표준화, 보존정책 합의 --json·storage.py·_developer()
2. 운영 강화 부서 단위 DLP 연계 마스킹, 중앙 DB 전환, 인증(Kerberos/SSO), 접근통제·감사로그, 인증서 MDM 배포 모듈 경계(masking/storage/identity)
3. 전사 전사 중앙 집중형/혼합형 게이트웨이 가용성 설계(LB·HA), 정책 자동화, 비용·사용량 리포팅 아키텍처 패턴·캡처 파이프라인 설계
교차 검증: 토큰·사용량 집계는 GitHub Copilot Metrics API의 조직 단위 지표와 교차 검증하는 것이 좋습니다(단, Metrics API는 프롬프트 원문을 제공하지 않으므로 원문 캡처는 이 프록시 경로로 분리해 설계).

확장 시 바뀌거나 깨지는 동작

규모를 키울 때 PoC 가정이 깨지는 지점을 미리 인지해야 합니다.

  • 프로세스/프로젝트 귀속: lsof 기반 소스포트→PID 역추적은 프록시와 클라이언트가 동일 머신일 때만 성립합니다. 중앙 집중형에서는 동작하지 않으므로 클라이언트 헤더 주입으로 대체해야 합니다.
  • SQLite 동시성: 단일 파일 SQLite는 고동시성 쓰기에 부적합합니다. 중앙 집중형은 중앙 RDBMS/SIEM으로 전환하세요(분산형은 로컬 SQLite 유지 후 배치 전송 가능).
  • 대시보드 노출면: 대시보드는 인증 없이 127.0.0.1에 바인딩됩니다. 중앙 운영 콘솔로 확장할 때는 인증·TLS·RBAC·열람 감사로그가 필수입니다. (실시간 이벤트에 원문 payload를 싣지 않는 PoC 설계는 운영에서도 유지할 가치가 있습니다.)
  • CA 인터셉트 충돌: 전사 trust store 배포는 인증서 pinning 앱·VPN·기존 기업 프록시와 충돌할 수 있습니다. 예외 목록과 즉시 teardown/원복 절차를 운영 표준에 포함하세요.
  • 데이터 보호 책임 증가: 수집 대상이 늘수록 프롬프트 원문에 포함된 소스코드·비밀· 개인정보의 저장 암호화, 최소수집, 목적 제한, 접근권한 분리, 보존·파기 정책의 중요도가 커집니다.

보안·한계

TLS 인터셉트와 사내 CA 신뢰 배포는 매우 강한 통제다. 실제 적용 전 보안, 법무, 개인정보/프라이버시 검토와 명시적 운영 정책이 필수다.

보안 고려사항

  • 프롬프트·응답 원문에는 소스코드, 토큰, 키, 개인정보, 영업비밀이 포함될 수 있다. 저장 위치, 접근권한, 암호화, 보존기간, 감사로그를 운영 정책으로 통제해야 한다.
  • config.yaml의 masking.enabled=true는 저장 전 정규식 기반 마스킹을 수행하지만 best-effort다. 모든 비밀정보 제거를 보장하지 않는다.
  • 기본 allowlist는 api.githubcopilot.com, copilot-proxy.githubusercontent.com, .githubcopilot.com, proxy.enterprise.githubcopilot.com이다. allowlist 밖 호스트는 캡처 저장 대상이 아니다.
  • 응답 저장은 capture.store_response와 capture.max_body_bytes의 영향을 받는다. 큰 본문은 기본 1MiB 상한에서 절단될 수 있다.
  • CLI의 --json 출력은 SIEM/DLP 연계의 출발점으로 사용할 수 있으나, 운영에서는 실시간 sink, 전송 보안, 실패 재시도, 중복 처리, 삭제 정책이 추가로 필요하다.

한계

  • 마스킹은 PoC 수준의 정규식 best-effort이며, 운영에서는 DLP 엔진 또는 비밀정보 스캐너와 연계해야 한다.
  • 토큰 산정은 응답 usage가 있으면 이를 우선하고, 없으면 tiktoken 또는 휴리스틱으로 추정한다. 조직 단위 비용 검증에는 GitHub Copilot Metrics API 등 별도 집계와 교차 검증이 필요할 수 있다.
  • 프로젝트 귀속은 터미널/CLI에서는 cwd 기반으로 정확도가 높지만, VS Code 같은 IDE는 공유 소켓과 다중 워크스페이스 특성상 best-effort다.
  • CA 신뢰와 시스템 프록시 설정은 인증서 pinning 앱, VPN, 기업 프록시, MDM 정책과 충돌할 수 있다. 장애 대응 절차에는 즉시 teardown, 네트워크 설정 원복, CA 제거 여부 확인이 포함되어야 한다.
