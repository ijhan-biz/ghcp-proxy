GitHub Copilot Proxy 기반 프롬프트 수집·관제 아키텍처

AI Agent(Claude · Codex · GitHub Copilot) 트래픽을 사내 Proxy로 중계·수집하는 구성의 가능 여부 검증 및 구현 가이드

2026-06-02 검증: GitHub 공식 문서 기준 대상: 인프라/보안/플랫폼 엔지니어 + AI 페어 구현 실행 전 보안·법무 검토 필요

0요약 (TL;DR)

결론: "GitHub Copilot은 Proxy 구조로는 불가능"은 사실이 아닙니다. Copilot도 Claude · Codex와 동일하게 사내 CA 기반 TLS 인터셉트(복호화) Proxy를 통해 프롬프트를 수집·모니터링하는 구성이 가능합니다. 단, custom certificate(사내 CA) 없이 단순 Proxy만 태우면 연결의 monitor/route/terminate만 가능하고 내용(payload)은 검사할 수 없습니다.
  • 가능 조건: Proxy URL은 http:// (https:// 미지원), 인증은 Basic / Kerberos, 사내 CA를 각 PC의 OS trust store에 설치, GitHub 도메인 allowlist 등록.
  • 프롬프트 원문 저장: GitHub native 기능이 아니라 TLS 인터셉트 Proxy에서 요청/응답 payload를 캡처하는 경로로 구현.
  • native Usage metrics(Copilot Metrics API): 집계 수치만 제공하고 프롬프트 원문은 포함하지 않음.

1아키텍처 개요

전 PC 트래픽을 사내 Forward Proxy / Gateway로 강제 라우팅하고, 사내 CA로 TLS를 인터셉트하여 복호화한 뒤 프롬프트·응답을 캡처·저장하고, 그 로그를 모니터링/이상탐지 파이프라인으로 흘려보내는 단일 관제 레이어 구성입니다.

┌──────────────┐ HTTPS(TLS) ┌───────────────────────────┐ re-encrypt ┌─────────────────────────┐ │ 개발자 PC │ ───────────────▶ │ 사내 TLS 인터셉트 Proxy │ ───────────────▶ │ Copilot / Claude / Codex│ │ (IDE + 확장) │ 사내 CA 신뢰 │ (Forward Proxy / Gateway) │ 공인 인증서 검증 │ 클라우드 엔드포인트 │ └──────────────┘ └─────────────┬─────────────┘ └─────────────────────────┘ ▲ │ 복호화된 요청/응답(payload) │ OS trust store에 사내 CA 설치 ▼ │ ┌───────────────────────────┐ └──────────────────────────────│ 수집/저장 + 토큰 산정 │ │ + SIEM / DLP / 이상탐지 │ └───────────────────────────┘
핵심 단서: custom certificate(사내 CA)가 없으면 Proxy는 "monitor / route / terminate"만 가능하고 트래픽 내용 검사는 불가합니다. 즉 프롬프트 원문 수집 = TLS 인터셉트가 전제입니다.

3Copilot 동작 전제 조건 (공식)

항목요구사항
Proxy URL 스킴http:// 로 제공. https:// 로 시작하면 현재 미지원.
Proxy 인증Basic(자격증명을 proxy URL에 포함) 또는 Kerberos
인증서사내 CA(custom certificate)를 OS trust store에 설치. NODE_EXTRA_CA_CERTS 파일도 인식
환경변수HTTPS_PROXY / https_proxy / HTTP_PROXY / http_proxy 순으로 Proxy URL 인식
특수 환경transparent proxy, Zscaler 지원
Allowlist 도메인api.githubcopilot.com, copilot-proxy.githubusercontent.com, *.githubcopilot.com 등

참고: Proxy / 인증서 설정 예시

# Basic 인증 포함 Proxy URL (예시)
export HTTP_PROXY="http://:@proxy.example.com:3128"
export HTTPS_PROXY="http://:@proxy.example.com:3128"

# 사내 CA 추가 인증서 (OS trust store 외 보조 경로)
export NODE_EXTRA_CA_CERTS="/etc/ssl/certs/corp-root-ca.pem"
// VS Code settings.json (Kerberos SPN 재정의가 필요한 경우)
{
  "http.proxy": "http://proxy.example.com:3128",
  "http.proxyKerberosServicePrincipal": "HTTP/proxy.example.com"
}
위 값은 형식 예시이며 실제 자격증명·도메인은 사내 환경에 맞게 교체하세요. 자격증명을 평문으로 노출하지 않도록 보안 정책을 따르세요.

4구현 단계 (AI 페어 구현용)

  1. 네트워크 강제 라우팅: 전 PC 아웃바운드를 사내 Forward Proxy/Gateway로 강제(투명 프록시 또는 PAC/시스템 프록시).
  2. TLS 인터셉트 구성: Proxy에 사내 CA 발급/배포, 인터셉트 정책 설정. Copilot 도메인을 복호화 대상에 포함.
  3. 클라이언트 인증서 배포: MDM/GPO로 사내 CA를 각 PC OS trust store에 설치(미설치 시 인증서 오류로 연결 실패).
  4. Allowlist 등록: Proxy/방화벽에서 GitHub Copilot 도메인 허용.
  5. 캡처·저장 파이프라인: 복호화된 요청/응답 payload를 정규화하여 저장(개발자/시간/모델/토큰 메타데이터 포함).
  6. 토큰 산정 + native 병행: 캡처 데이터로 토큰 산정, Copilot Metrics API로 조직 단위 집계 보강.
  7. 이상탐지 연계: 수집 로그를 SIEM/DLP/이상탐지 룰에 연결, 마스킹/보존정책 적용.
  8. 검증: Copilot 정상 동작(완성/Chat) + 캡처 정상 + 인증서 오류 없음 확인.
AI에게 그대로 전달할 수 있는 작업 프롬프트

"사내 Forward Proxy(예: Squid/Envoy/사내 Gateway)에서 GitHub Copilot 트래픽을 사내 CA로 TLS 인터셉트하여 요청/응답 payload를 캡처·저장하는 구성을 만들어줘. 조건: Proxy URL은 http://, 인증은 Basic 또는 Kerberos, 사내 CA는 각 PC OS trust store에 배포, allowlist에 api.githubcopilot.com / copilot-proxy.githubusercontent.com / *.githubcopilot.com 포함. 캡처 로그는 개발자·시간·모델·토큰 메타데이터와 함께 저장하고 SIEM/DLP로 전달하는 파이프라인까지 설계해줘. 민감정보 마스킹과 보존정책도 포함."

5검증 체크리스트

  • Proxy URL이 http:// 스킴인가 (https:// 아님)
  • 사내 CA가 각 PC OS trust store에 설치되었는가
  • Copilot 도메인이 allowlist에 등록되었는가
  • 인증(Basic/Kerberos)이 정상 동작하는가
  • TLS 인터셉트 후 Copilot 완성·Chat이 정상 동작하는가
  • 요청/응답 payload가 정상 캡처·저장되는가
  • 토큰 산정 값이 합리적인가 (필요 시 Metrics API와 교차 확인)
  • 민감정보 마스킹 / 로그 보존정책이 적용되었는가
  • 보안·프라이버시·법무 검토가 완료되었는가

6보안 · 운영 유의사항

강한 통제: TLS 인터셉트는 전사 PC에 사내 CA를 신뢰시키는 구성입니다. GitHub 공식 문서도 "사내 인증서 설치는 해당 인증서 발급자가 모든 인터넷 트래픽을 가로챌 수 있게 한다"고 경고합니다. 반드시 보안·프라이버시 정책 및 법무 검토를 수반하세요.
  • 프롬프트 원문에는 소스코드·비밀정보가 포함될 수 있으므로 저장 시 마스킹/암호화/접근통제/보존기간 정책이 필요합니다.
  • 인증서 오접속/오류 시 "인증서 오류 무시" 설정은 보안 위험이 있어 공식 문서에서도 권장하지 않습니다.
  • native Usage metrics는 집계 지표만 제공하므로 원문 저장 요건은 Proxy 캡처 경로로 분리 설계하세요.
